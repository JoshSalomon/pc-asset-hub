================================================================
Summary
================================================================

The Milestone 36 test matrix is broad and materially stronger than most feature plans: it spans unit/API/browser/system/live layers, includes protocol seam tests, and explicitly covers many failure paths (timeouts, malformed JSON, oversized responses, orphaned bindings). That gives a solid baseline for reliable implementation.

The plan still has a few high-risk gaps that would let two competent engineers build different behaviors and still “pass tests.” The biggest problems are (1) one explicitly unresolved acceptance criterion, (2) contradictory health-state semantics across artifacts, and (3) security/operational edge cases around auth, watcher lifecycle, and startup sync that are not pinned by concrete tests. These are fixable now and should be resolved before implementation starts.

================================================================
Critical Findings
================================================================

1. **`T-36.83` is explicitly non-deterministic (two opposite outcomes allowed).**
- **Description of the issue:** `T-36.83` says UpdateBinding on orphaned exporter can either succeed or fail, as long as behavior is documented.
- **Why it matters:** This is not testable as a contract. Different implementations can pass while delivering opposite UX and API semantics.
- **Specific location:** `docs/test-plan-detailed.md`, Milestone 36 → Step 9 → `T-36.83`; mirrored as “decision pending” in `docs/test-plan.md`, section `5.53`.
- **Suggested fix or question to resolve:** Decide one behavior now (recommended: allow `enabled`-only updates without exporter validation), then split into explicit unit+API+browser assertions.

2. **Health classification semantics conflict between design and test plan.**
- **Description of the issue:** Design state machine says non-200/timeout maps to `Unhealthy`, but detailed tests require `401/403` to map to `Error`.
- **Why it matters:** Status drives operator diagnostics and UI color/state; conflicting semantics create inconsistent implementations and regressions.
- **Specific location:** `docs/plans/2026-05-28-dynamic-export-plugins-design.md`, “Health Status State Machine” and health probe behavior; `docs/test-plan-detailed.md`, Step 8 (`T-36.66`, `T-36.67`).
- **Suggested fix or question to resolve:** Pick one mapping and normalize all artifacts. If auth rejection is intentionally distinct, update the design state machine explicitly.

================================================================
High Findings
================================================================

1. **Initial informer sync gate is missing in the detailed test matrix.**
- **Description of the issue:** Context requires not serving requests until initial CR list/sync completes, but no corresponding detailed test exists.
- **Why it matters:** Startup race can temporarily hide existing exporters, causing false orphaned errors and failed binding operations.
- **Specific location:** Requirement appears in `docs/test-plan.md`, section `5.53` Step 10; absent from `docs/test-plan-detailed.md` Milestone 36 Step 10.
- **Suggested fix or question to resolve:** Add a dedicated startup-sync test and an API-level assertion that `/exporters` is not served with a partially initialized registry.

2. **Trusted subject contract is internally inconsistent and under-tested.**
- **Description of the issue:** Default SA naming differs (`assethub-api` vs `assethub-api-server`), and tests do not validate default-vs-explicit `trustedSubjects` behavior.
- **Why it matters:** Can cause production auth failures (all probes/exports denied) or accidental over-trust.
- **Specific location:** `docs/plans/2026-05-28-dynamic-export-plugins-design.md` Auth Contract section; `docs/plans/2026-06-03-dynamic-export-plugins-impl-plan.md`; live auth tests in `docs/test-plan-detailed.md` (`T-36.135`–`T-36.137`).
- **Suggested fix or question to resolve:** Canonicalize SA names across all docs and add live tests for omitted `trustedSubjects` defaults plus explicit custom allowlists (including operator SA health probe success).

3. **Security boundary for webhook endpoint trust is not defined/tested.**
- **Description of the issue:** No explicit requirement constrains `spec.endpoint` trust domain (cluster-local vs arbitrary external), while bearer tokens are always sent.
- **Why it matters:** Misconfigured/malicious CR can exfiltrate service-account tokens to arbitrary endpoints.
- **Specific location:** Auth + endpoint behavior in design/impl docs; tests in `docs/test-plan-detailed.md` validate header presence but not endpoint trust controls.
- **Suggested fix or question to resolve:** Define endpoint policy (e.g., cluster-local service DNS only) and/or audience-scoped tokens; add negative tests for disallowed endpoints.

4. **Informer delete-path robustness is not covered (tombstones/idempotency).**
- **Description of the issue:** Detailed tests cover normal delete but not `DeletedFinalStateUnknown` tombstones or repeated/out-of-order watch events.
- **Why it matters:** Real informer streams can produce tombstones; missing handling can leave stale exporters or cause crashes.
- **Specific location:** `docs/test-plan-detailed.md`, Step 10 (`T-36.109` only covers direct deregister).
- **Suggested fix or question to resolve:** Add watcher unit tests for tombstone delete handling and idempotent add/update/delete event sequences.

5. **Phase gating counts are inconsistent inside the same document.**
- **Description of the issue:** Phase A “tests that must pass” includes `T-36.144` but claims `1348`; Phase A exit criteria also says `1348` but only through `T-36.125`; human checkpoint still references `802`.
- **Why it matters:** Wrong gates let work be marked complete with unrun suites.
- **Specific location:** `docs/test-plan-detailed.md` Overview Phase A and Milestone 36 phase-exit block.
- **Suggested fix or question to resolve:** Publish one authoritative count and explicitly split Phase A-required tests from Phase B/live/system tests.

Medium Findings
================================================================

1. **Timeout semantics are inconsistent across artifacts.**
- **Description of the issue:** One path says `timeoutSeconds=0` rejected by CRD; another says omitted/0 defaults to 10; context also mentions clamping 1→3.
- **Why it matters:** Implementation can diverge between unit behavior and live cluster behavior.
- **Specific location:** `docs/test-plan-detailed.md` Step 7 (`T-36.64`), `docs/plans/2026-06-03-dynamic-export-plugins-impl-plan.md` Step 10 timeout semantics, `docs/test-plan.md` Step 10 notes.
- **Suggested fix or question to resolve:** Make CRD validation/defaulting the single source of truth and remove impossible runtime cases from watcher tests (or label them unit-only malformed-object tests).

2. **Orphaned single-run API contract is underspecified.**
- **Description of the issue:** `T-36.85` expects an “error” but does not pin status code/response schema.
- **Why it matters:** Client/UI behavior can drift on 400 vs 404 vs 500 handling.
- **Specific location:** `docs/test-plan-detailed.md`, Step 9 `T-36.85`.
- **Suggested fix or question to resolve:** Specify exact HTTP status and error payload shape; assert both in API and browser tests.
